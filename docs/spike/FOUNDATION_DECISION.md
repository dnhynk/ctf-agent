# FOUNDATION_DECISION

작성일 2026-08-07. 상태: **판정 미기재.** 이 문서는 결정을 담고 있지 않고, 결정을 기계적으로 만들기
위한 도구다.

## 이 문서가 하는 일

1. 세 선택지(OSS fork / component extraction / greenfield)가 각각 무엇을 떠안는지 적는다.
2. 그 셋을 가르는 관측이 무엇인지 **미리** 고정한다.
3. 그 관측을 만드는 foundation spike를 명세한다.
4. 판정란을 비워 둔다. 스파이크가 끝난 뒤 §12를 채우는 것이 결정이다.

## 이 문서가 하지 않는 일

- foundation을 오늘 고르지 않는다. 오늘 고를 수 있는 근거는 명성·논문 점수·이미 쓰인 코드량뿐이고,
  셋 다 근거로 쓸 수 없다.
- 최종 spec, 디렉터리 구조, agent loop, Planner/Executor 채택 여부를 정하지 않는다.
- solve rate를 예측하지 않는다. 스파이크는 성능을 재지 않는다(§9).

  아래에서 그런 진술은 `[pack §x.y]`로 표시했고, 전부 **미검증**이다.
- **현 저장소의 소스는 열지 않았다.** 프로토타입에 관한 진술은 전부
  `docs/evidence/2026-08-07-phase-b-evidence.md`에서만 인용했고 `[ev §x]`로 표시했다.
- **이 세션에서 실행한 명령은 문서 읽기뿐이다.** 이 문서에 등장하는 수치 중 이 세션에서 측정된 것은

### 2.2 인프라에서 오는 제약

`203.0.113.10`, Ubuntu 24.04, 8 vCPU / 16 GiB / 320 GiB, Docker 29.7.1, **`/dev/kvm` 없음** [ev §2].

- KVM이 없으므로 VM 기반 격리(Firecracker 등)는 선택지가 아니다. 격리는 컨테이너 단독이고, 세 선택지
  모두 같은 조건에서 시작한다. **격리 강도는 후보 간 차별점이 아니다.**
- 8 vCPU / 16 GiB는 동시 실행 arm 수를 제한한다. 스파이크는 순차 실행을 기본으로 한다.
- 320 GiB는 프로토타입 데이터와 공유한다. Kali 계열 이미지를 포함한 후보별 이미지가 수십 GiB를
  차지할 수 있다 → `HOST_EXCEPTIONS.md` §4.

### 2.3 모델·비용에서 오는 제약

`config/models.yaml` / `config/pricing.openai.yaml` 기준.

- 사용 가능한 provider는 OpenAI 하나다. `gpt-5.6-terra`(입력 $2.00/M, 캐시 입력 $0.20/M, 출력
  $12.00/M), `-luna`, `-sol`. `gpt-5.3-codex`는 cache-write 단가가 없어 선택 시 실패한다.
- 입력 272K 토큰을 넘기면 **요청 전체가** 2배(입력)/1.5배(출력)로 재과금된다. 유형 B의 장출력과
  유형 C의 요청 히스토리는 이 경계를 넘길 수 있는 두 경로다. 스파이크는 이 경계 아래에서 돌도록
  설계하고, 넘긴 arm은 그 사실 자체를 관측으로 기록한다(S5/S6 부적합 신호).
- 이 제약이 후보 선택에 주는 함의가 하나 있다. research pack이 인용한 최고 성적은 Claude 4.5 Opus
  59% / Gemini 3 Pro 52%이고, 같은 표에서 GPT 계열은 13.5~18%다 [pack §5.1]. **우리가 쓸 수 있는
  모델은 그 표에서 하위권이다.** 따라서 어떤 후보의 published score도 우리 조건의 기대치가 아니며,
  이는 세 선택지 중 특정 하나를 지지하거나 반대하는 근거가 아니라 **published score를 근거에서
  제외해야 하는 이유**다.

## 3. foundation contract — 9개 seam

지시받은 흐름을 9개 이음매로 쪼갠다. 이것이 스파이크의 채점표이자, 세 선택지 모두가 뒤에 놓여야 할
계약이다(§8). 아래 표는 seam의 정의이고, 기계적으로 판정 가능한 술어와 프로브는
`docs/spike/SEAM_CONTRACT.md`에 있다.

| # | seam | 통과 조건(관측 가능해야 함) | 나중에 바꾸는 비용 |
|---|---|---|---|
| S1 | challenge 입력 | 챌린지 기술·입력물이 해시와 함께 attempt에 바인딩된다. 하니스가 자기 벤치마크 형식 외의 챌린지를 받을 수 있다 | **낮음** (단, 후보 쪽 결합도 시험) |
| S2 | workspace 격리 | `/input` 읽기전용, `/work`·`/artifacts` 쓰기, 그 밖 경로 거부. 네트워크는 선언된 것만. attempt 종료 시 컨테이너·프로세스 0 잔존 | **높음** — 위에 전부가 얹힌다 |
| S3 | 모델 추론 | provider 어댑터가 core loop 밖에 있다. 토큰·비용이 호출 단위로 회계된다 | 낮음. 단 provider 이름이 core에 박혀 있으면 높음(조기 중단 조건) |
| S4 | 도구 실행 | 1회 명령 / **모델 턴을 가로질러 살아있는 세션** / 상태를 유지하는 HTTP 요청 — 셋이 같은 도구 계층에서 표현된다 | **높음** — 유형 B/C의 결정 지점 |
| S5 | 실행 결과 관찰 | 출력이 결정론적으로 잘리거나 요약되고, 잘린 원본은 artifact로 남으며 그 artifact에 생산 이벤트가 있다 | 중~높음 |
| S6 | 상태 유지 | 세션 핸들·쿠키·이전 관찰이 모델 턴을 넘어 살아남는다. 컨텍스트 압축이 상태를 지우지 않는다 | **높음** |
| S7 | flag 후보 추출 | 후보 문자열이 **어느 관찰에서 나왔는지**와 함께 기록된다 | 낮음 |
| S8 | flag 검증 | verifier가 solver 밖에 있고, 정답은 worker가 도달할 수 없는 곳에 있다 | 중간. 단 늦게 고치면 그 전 결과가 전부 무효 |
| S9 | telemetry 저장 | `EVAL_CONTRACT.md`의 통제 조건 전부와 모델 호출·도구 입출력·비용·타임스탬프가 기록에서 재구성된다 | 중~높음 (이벤트 소싱이 아니면 높음) |

**이 표의 요점은 순서가 아니라 마지막 열이다.** foundation은 "오늘 무엇이 잘 도는가"가 아니라
"틀렸을 때 되돌릴 수 없는 가정이 무엇인가"로 고른다. S2·S4·S6이 그것이고, 셋 다 유형 B와 C에서만
하중을 받는다. 그래서 스파이크의 무게중심은 유형 B·C다.

S7과 S8에 붙은 두 조건은 pack §9.2의 anti-cheat 요구에서 왔고, 프로토타입은 그중 하나를 실제로
어겼다: 도구 artifact에 생산 이벤트가 없어 해시를 어떤 이벤트에서도 인용할 수 없었다 [ev §8.4].
쉽게 틀리는 지점이라 통과 조건에 명시한다.

## 4. 세 유형이 싣는 하중

| | 유형 A 정적 분석 | 유형 B 인터랙티브 세션 | 유형 C 웹 상태 |
|---|---|---|---|
| 주로 시험하는 seam | S1 S2 S4 S5 S7 S8 S9 | **S2 S4 S5 S6** | **S4 S6** + S2(대상 네트워크) |
| 고유 요구 | 여러 관찰의 종합, artifact 크기 | 모델 턴을 가로지르는 프로세스 수명, PTY 의미론, interrupt/timeout, 프로세스 트리 정리, 동시 세션 | 쿠키·세션 유지, 요청 히스토리, 요청 출처, (선택) 동시 요청 |
| 역할 | **대조군.** 리그가 동작함을 보이는 스모크 | **판별자 1** | **판별자 2** |

유형 A를 통과하지 못하는 후보는 없을 것으로 본다. 그래서 유형 A는 후보를 가르지 못하고, 대신
"우리 챌린지·우리 verifier·우리 telemetry를 물릴 수 있는가"(S1·S8·S9)를 재는 데 쓴다.

유형 B가 판별자인 근거는 pack이 명시적으로 남긴 비대칭이다: D-CIPHER 논문은 EnIGMA와 달리 advanced
interactive interface를 구현하지 않았다고 스스로 밝히고 [pack §5.2], EnIGMA의 핵심 기여가 바로 그
interactive tool 계층이다 [pack §5.3]. 즉 "명령 1회 실행"으로 설계된 도구 계층 위에 지속 세션을
나중에 얹는 일이 실제로 얼마나 드는지가 이 스파이크가 답해야 할 질문이다.

유형 C가 판별자인 근거는 SmartData 연구의 실패 분류다: XSS는 브라우저/JS 실행 환경 부재, blind
injection은 긴 stateful 추출에서의 컨텍스트 붕괴, race condition은 순차 런타임으로 동시성을 표현할
수 없었던 것 [pack §5.5]. 셋 다 모델 실패가 아니라 **런타임 계약 실패**다.

## 5. 선택지 1 — OSS fork

대상: TATAR-LAB `ctf-agents`(1순위). D-CIPHER upstream은 그 상위집합 관계 때문에 스파이크 arm에서
제외한다(§9.1).

### 5.1 유지하게 되는 구조적 가정

전부 [pack §5.1·§5.2] 기준이며 미검증이다. Stage 0에서 코드로 확인해야 한다.

1. **2-agent 분해.** Planner가 전략과 상태를 들고, Delegate마다 fresh-context Executor가 생긴다.
   Planner만 flag 제출·포기를 할 수 있다.
2. **대화 로그가 곧 상태.** 상태 관리가 truncation(최근 5개 Executor action/observation 유지)이다.
   구조화된 상태 저장소가 아니다.
3. **명령 1회 실행이 기본 도구 형태.** 지속 세션이 1급 시민이 아니다.
4. **성공 판정이 느슨하다.** 원 논문은 "대화 어딘가에서 correct flag가 관측되면" solved로 셌다.
   우리 `EVAL_CONTRACT.md`와 정면으로 충돌한다.
5. **종료가 round/cost 기준.** wall-clock이 1급 종료 조건이 아니다 → `OBJECTIVE.md` 2순위와 어긋난다.
6. **챌린지 입력이 NYU CTF Bench 형태**이고 Docker 수명주기를 벤치마크 러너가 소유한다.
7. **provider function-calling 형식 의존**, 그리고 fork가 추가한 다수 backend(Vertex/OpenRouter/
   Ollama/Gemini).

1·2·5는 잘못된 가정이라는 뜻이 아니다. **포크하면 이 가정들을 우리가 고른 적 없이 물려받는다**는
뜻이고, 그중 4는 반드시 교체해야 하며 2·5는 유형 B/C에서 문제를 일으킬 후보다.

### 5.2 필요한 변경 범위

| seam | 해야 하는 일 | 규모 |
|---|---|---|
| S8 | 성공 판정을 하니스에서 떼어내 외부 verifier로 교체. 하니스 자체 점수 보고를 끈다 | 필수, 중간 |
| S9 | `EVAL_CONTRACT.md` 통제 조건 전부를 남기는 이벤트 계층 추가 또는 교체 | 필수, 중~큼 |
| S2 | 벤치마크 러너가 소유한 컨테이너 수명주기를 제품 격리 모델과 화해시킨다. `SAFETY_SCOPE.md`의 마운트·네트워크 규칙 적용 | 필수, 큼 |
| S1 | 자작 챌린지를 NYU 형식이 아닌 채로 넣을 수 있게 한다(또는 어댑터) | 중간. **이 비용 자체가 관측치다** |
| S4·S5·S6 | 지속 세션(유형 B)과 상태 유지 HTTP(유형 C)를 도구 계층에 추가 | **미지. 스파이크가 답해야 할 것** |
| S3 | 쓰지 않는 backend 정리, 예산·토큰 회계 연결 | 작음 |
| S7 | 후보에 출처(생산 관찰 id) 부착 | 작음 |

S4·S5·S6이 "3개 이하의 구조 패치"로 되면 포크가 유력해지고, core rewrite가 필요하면 pack §14의
조기 중단 조건("interactive/browser/concurrency 확장에 core rewrite가 필요")에 그대로 걸린다.

### 5.3 예상되는 기술 부채

1. **평가 의미론의 이중화.** 느슨한 성공 판정이 로그·메트릭·리포트 전반에 퍼져 있는 상태에서 verifier만
   갈아끼우면 성공의 정의가 두 개 공존한다. 나중에 어느 숫자가 어느 정의인지 추적 불가능해진다.
2. **벤치마크-솔버 결합.** 러너가 챌린지 수명주기를 소유하면 제품에서는 러너를 쓸 수 없는데 솔버 코드가
   러너의 가정을 계속 참조한다. pack §14가 조기 중단 조건으로 명시한 항목이다.
3. **상태 이중화.** 최근 N개 관찰 truncation 위에 지속 세션을 얹으면 "모델이 기억하는 상태"와 "런타임이
   들고 있는 상태"가 갈라진다. pack이 보고한 soliloquizing(모델이 관찰 없이 관찰을 지어내는 현상,
   [pack §5.3])의 구조적 원인이 정확히 여기다.
4. **죽은 backend 유지비.** 우리는 provider 1개만 쓰는데 여러 backend의 예외 분기를 계속 안고 간다.
5. **이미지 부채.** Kali 계열 100+ 도구는 디스크·빌드 시간이고, 그중 어떤 도구가 실제로 쓰이는지에 대한
   근거는 없다. pack §5.1 caveat 6이 같은 지적을 한다.
6. **upstream 단절.** 연구 코드에는 유지보수 약속이 없다. 포크 후 병합은 사실상 중단되고, 우리가 전부
   떠안는다.

### 5.4 성능 검증 방법

- **스파이크 시점(성능 아님, 건전성):** §9.3의 seam 판정 + 운영 관측 — 세션 유지 성공률, 프로세스 잔존
  수, 컨텍스트 초과 횟수, 타임아웃, 정리 실패, 272K 경계 초과 횟수.
- **채택 후:** `EVAL_CONTRACT.md` 그대로. 단 이 선택지에는 전제가 하나 붙는다 — **후보 자체의 점수
  보고를 끄고 우리 verifier만 쓰는 상태에서 첫 측정을 한다.** 그러지 않으면 첫 숫자가 어느 성공 정의로
  나온 것인지 영원히 알 수 없다.
- 물려받은 ablation(Ubuntu vs Kali, tool discovery on/off, AutoPrompt on/off, Planner on/off)은
  성능 단계의 자산이다. 한 번에 한 변수만 바꾼다 [pack §10 Stage 3].

### 5.5 실패 시 철수 방법

- **철수 조건(사전 등록):**
  (a) 유형 B 또는 C가 구조 패치 4개째를 요구한다,
  (b) 채택 후 S9 telemetry를 `EVAL_CONTRACT.md` 수준으로 만들 수 없다,
  (c) Stage 0에서 LICENSE 또는 의존성 라이선스가 제품 목적과 충돌한다.
- **철수 방법:** 포크는 **별도 remote로만** 유지하고, 제품 코드는 fork 내부 심볼을 직접 참조하지 않으며
  §3 계약 어댑터 뒤에서만 호출한다. 철수 = 어댑터 구현 교체. **이 규칙을 지키지 않으면 철수 비용은
  사실상 무한대가 된다. 이것은 포크 채택의 권고가 아니라 전제 조건이다.**
- **잃는 것:** 스파이크 시간 + 어댑터 작성 비용. **남는 것:** seam contract, 자작 챌린지 3종,
  telemetry 스키마, verifier — 전부 선택지와 무관하게 재사용된다.

## 6. 선택지 2 — component extraction

대상 후보 컴포넌트(전부 미검증, MIT로 보고됨 [pack §4] — Stage 0에서 재확인):

| 컴포넌트 | 출처 | 채우려는 seam |
|---|---|---|
| InteractiveSession 런타임 (PTY, GDB, netcat/REPL, 장출력 요약, 세션 timeout/cleanup) | EnIGMA / SWE-agent **v0.7.0 (`dc18a74`)** | S4 S5 S6 (유형 B) |
| solver와 제출·검증의 분리, 로컬 flag 검증·캐시 | CTFusion | S8 |
| tool discovery 인터페이스(`ListCommandsTool`/`LookupCommandTool` + 문서 CSV) | TATAR | S4 |
| 도구 이미지·패키지 목록 (코드가 아니라 기반) | TATAR Kali 프로필 | S2 S4 |

> EnIGMA는 반드시 `v0.7.0` 태그를 쓴다. SWE-agent README가 EnIGMA 업데이트 완료 전까지 0.7을 쓰라고
> 명시한다 [pack §5.3]. `main`을 논문 구현으로 취급하면 안 된다.

### 6.1 유지하게 되는 구조적 가정

- **원칙적으로 컴포넌트 경계에서 끊긴다.** 이것이 이 선택지의 유일한 진짜 장점이다.
- **단, 계약을 우리가 먼저 쓰지 않으면 그 장점이 사라진다.** 컴포넌트를 먼저 들여오고 나중에 계약을
  맞추면 컴포넌트의 가정이 그대로 제품 도메인이 된다.
- 개별적으로 남는 가정 두 가지:
  - EnIGMA 세션 런타임은 SWE-agent 0.7의 환경/배포 계층 위에 있다 [pack §5.3]. 그 계층을 얼마나
    끌고 와야 하는지가 추출 비용의 대부분이고, **현재 미지다.**
  - EnIGMA의 관찰 포맷은 세션과 함께 설계되었다. 세션만 가져오고 관찰 포맷을 우리 것으로 쓰면 원본이
    그 포맷을 전제로 얻던 이득의 일부가 사라질 수 있다. pack §10 Stage 3이 이걸 별도 ablation으로
    분리해 두었다(`EnIGMA observation format vs common normalized format`).

### 6.2 필요한 변경 범위

1. §3의 계약, 특히 세션 계약을 **먼저** 확정한다. pack §5.3이 제시한 형태를 출발점으로 쓴다:
   `start / send / read(timeout, max_bytes) / interrupt / snapshot / close`.
2. 후보 컴포넌트를 `vendor/<candidate>-<commit>/`에 커밋 단위로 격리하고, 제품 코드는 어댑터 파일
   하나를 통해서만 접근한다.
3. 나머지 seam(S1 S2 S3 S7 S8 S9와 agent loop 전체)은 자작한다. 즉 **이 선택지의 실제 작업량은
   greenfield에서 S4/S5/S6를 뺀 것**이다.
4. `LICENSE_MATRIX.md`를 파일 단위 출처와 함께 유지하고, 고지 의무를 릴리스 절차에 넣는다.

### 6.3 예상되는 기술 부채

1. **남의 코드의 실패 모드를 디버깅하는 비용.** 하필 추출 대상이 PTY·프로세스 그룹 영역인데, 이 저장소는
   같은 영역에서 이미 세 종류의 결함을 실측으로 발견했다: `killpg`가 job control 하의 백그라운드 잡을
   못 지운 것, 죽인 자식이 좀비로 남아 생존자로 계산된 것, `waitpid(WNOHANG)`의 상태 0이 "정상 종료"와
   구분되지 않은 것 [ev §8.1–8.3]. 남의 구현에서 같은 종류를 만나면 진단 비용은 더 크다.
2. **경계 침식.** 어댑터는 얇게 시작해 두꺼워지고, 결국 컴포넌트 내부 개념이 제품 도메인으로 샌다.
3. **upstream 이탈.** vendored 코드는 갈라지고 보안 패치가 자동으로 오지 않는다.
4. **부분 채택의 함정.** §6.1의 두 번째 항목 — 잘라낸 조각이 잘라낸 만큼만 효과를 낸다는 보장이 없다.

### 6.4 성능 검증 방법

**세 선택지 중 검증이 가장 깨끗하다.** 컴포넌트가 계약 뒤에 있으므로 on/off A/B가 성립한다.

- 유형 B를 자작 최소 세션 구현 vs 추출한 EnIGMA 런타임으로 각각 돌리고, 계약을 고정한 채 구현만 바꾼다.
  차이는 그 컴포넌트에 귀속된다.
- 같은 방식으로 tool discovery on/off, 관찰 포맷 원본 vs 정규화를 분리한다.
- 이 A/B가 성립하려면 계약이 먼저 있어야 한다. 계약 없이 들여오면 이 선택지의 검증 이점 자체가 사라진다.

### 6.5 실패 시 철수 방법

- **철수 조건:** 어댑터를 유지하려고 vendor 원본을 반복 수정하게 되는 시점(= 사실상 REWRITE),
  또는 Stage 0의 라이선스 재확인 실패, 또는 SWE-agent 0.7 계층을 끌고 오는 범위가 컴포넌트보다 커질 때.
- **철수 방법:** `vendor/` 디렉터리 삭제 + 어댑터 파일 재작성. 계약과 그 계약에 대한 테스트는 남는다.
- **잃는 것:** 어댑터 + vendor 이해 비용. **가장 싼 철수다.**

## 7. 선택지 3 — greenfield

### 7.1 유지하게 되는 구조적 가정

greenfield는 "가정이 없다"가 아니라 **"가정이 canon과 인프라에서만 온다"**는 뜻이다. 물려받는 것:

- provider 1개(OpenAI), 모델 `gpt-5.6-*`, 272K 재과금 경계 (§2.3)
- KVM 없는 컨테이너 단독 격리, 8 vCPU / 16 GiB (§2.2)
- 호스트 측 오케스트레이션, worker에 키를 넣지 않음, manifest 선언 대상만 접근, 제출은 사람
  (`SAFETY_SCOPE.md`)
- 성공은 verifier 통과, 통제 조건 재구성 가능 (`EVAL_CONTRACT.md`)

여기서 명확히 해 둘 것: **이 저장소의 기존 코드를 재사용하는 것은 greenfield의 정의에 포함되지 않는다.**
기존 코드가 있다는 사실은 이 선택지를 지지하는 근거가 아니고(운영자 지시, pack §13 규칙 2), 반대로
그것이 있다는 이유로 배제할 이유도 없다. 이 문서는 그 질문을 **결정 이후로 미룬다**(§13).

### 7.2 필요한 변경 범위

9개 seam 전부를 만든다. 규모의 차이를 정직하게 적으면:

| seam | 자작 난이도 | 근거 |
|---|---|---|
| S1 S3 S7 | 낮음 | 형식·어댑터·문자열 매칭 |
| S8 S9 | 중간 | 설계는 명확하다(§3). 분량이 있을 뿐 |
| S2 | 중간 | 컨테이너 격리는 알려진 문제이고 KVM 부재로 선택지도 좁다 |
| **S4 S5 S6** | **높음, 그리고 이 선택지의 전부** | 유형 B/C의 런타임 계약 |

S4/S5/S6를 자작으로 통과시킬 수 있는가 — 이것이 선택지 3의 유일한 질문이다. 그래서 스파이크에는
**greenfield arm이 반드시 포함되어야 한다**(§9.1). 이 arm이 없으면 두 OSS 선택지만 시험받고 세 번째는
가설로 남아, 스파이크 자체가 OSS 쪽으로 기운다.

**그리고 그 arm은 위 표의 마지막 행만 재면 된다.** S1·S3·S7을 낮음으로, S8·S9·S2를 중간으로 판정해
놓고 probe로 다시 재는 것은 낭비다. 따라서 greenfield arm은 전체 러너가 아니라 **§4
`InteractiveSession` 계약의 참조 구현**으로 좁힌다(운영자 합의 2026-08-07). 부수 효과가 하나 있고
그것도 필요하다: 참조 구현은 계약이 만족 가능하다는 존재 증명이므로, 검사기 술어 자체가 옳은지
확인할 수단이 된다. 지금은 그 수단이 없다.

### 7.3 예상되는 기술 부채

1. **재발견 부채.** 장출력 요약, 컨텍스트 초과, 세션 정리, ANSI/프롬프트 에코 — 이미 알려진 함정을 다시
   밟는다. 이 저장소가 [ev §8]에서 세 번 밟았다는 것이 그 부채의 관측 증거다.
2. **도구 목록에 근거가 없다.** 프로토타입의 6개 프로필 패키지 목록은 **어떤 챌린지 코퍼스도 참조하지
   않고** 골랐고, 검증된 것은 이미지가 빌드되고 격리 assertion을 통과한다는 것뿐이다 [ev §9]. 자작하면
   이 부채를 다시 진다. TATAR의 도구 목록·문서 CSV는 이 부채를 덜어 주는 유일한 외부 자산이다.
3. **브라우저·동시성.** 유형 C의 상위 요구(JS 실행, race)는 자작 비용이 크고, 미루면 웹 카테고리가
   구조적으로 막힌다 [pack §5.5].
4. **대조군 유지 부채.** 비교 대상이 없으면 성능 주장을 할 수 없다. 대조군을 계속 돌리는 것 자체가
   지속 비용이다.

### 7.4 성능 검증 방법

- 스파이크 시점: 다른 arm과 동일한 §9.3 판정. 추가로 **참조 구현을 §4.1의 네 요구까지 통과시키는 데
  실제로 든 시간을 기록한다.** 이 숫자가 선택지 3의 비용 논거 중 유일하게 관측된 것이 된다. 추정하지
  않는다. 범위가 세션 런타임으로 좁아졌으므로 이 숫자를 9개 seam 전체의 비용으로 외삽하지 않는다.
- 채택 후: `EVAL_CONTRACT.md`. 단 이 선택지에는 조건이 붙는다 — **외부 대조군(Codex CLI)을 같은 조건에서
  계속 유지해야 한다.** 대조군 없는 greenfield는 어떤 성능 주장도 할 수 없고, "우리가 만들었으니 낫다"는
  pack §13 규칙 12가 금지한 논법이다.

### 7.5 실패 시 철수 방법

**세 선택지 중 철수가 가장 비싸다. 시간은 되돌아오지 않는다.** 그래서 완화책은 사후가 아니라 사전이다.

- **철수 조건(사전 등록):** 참조 구현이 §4.1의 네 요구와 유형 B 프로브를 스파이크 안에서 통과시키지
  못하면, 선택지 3은 그 자리에서 탈락한다. 채택 후로 미루지 않는다. **이것이 이 선택지의 주된
  안전장치다.**
- **채택 후 철수 조건:** 유형 C의 브라우저/동시성 요구에서 같은 일이 반복되면 그 seam만 §6으로 전환한다.
- **철수 방법:** 처음부터 §3 계약을 인터페이스로 두고 자작 구현을 그 뒤에 둔다. 철수 = 그 구현만 교체.
  선택지 2와 물리적으로 동일한 구조이며, 실제로 greenfield와 extraction은 **한 축의 두 지점**이지
  배타적 선택지가 아니다.

## 8. 세 선택지에 공통으로 걸리는 전제

위 세 절의 철수 방법이 전부 같은 문장으로 끝난다. 그것이 이 문서의 결론에 가장 가까운 것이다.

> **§3의 seam contract를 먼저 쓰고, 어떤 선택지든 그 계약 뒤에 놓는다.**
> 계약이 없으면 fork는 철수 불가능해지고, extraction은 검증 이점을 잃고, greenfield는 대조군을 잃는다.
> 계약은 세 선택지 중 무엇을 고르든 버려지지 않는 유일한 산출물이다.

따라서 이 계약을 쓰는 작업은 결정을 기다릴 필요가 없고, 스파이크의 선행 조건이다.
초안은 `docs/spike/SEAM_CONTRACT.md`(2026-08-07). 확정판은 §13.1에서 만든다.

> **개정 2026-08-07 (운영자 결정, 세션 D). `foundation-spike` 프로파일에 한해
> `reasoning effort medium` → `none`. 전문과 근거는 `docs/adr/ADR-0001`.**
>
> **이것은 영구 변경이 아니다.** `EVAL_CONTRACT.md`는 고치지 않았고, 제품·성능 평가
> 프로파일은 **`Responses API + medium`을 유지한다.** 아래 두 프로파일로 분리한다.
>
> | | `foundation-spike` (지금) | `target-performance` (후속 gate) |
> |---|---|---|
> | endpoint | T·E `/v1/chat/completions`, X `/v1/responses` | 전부 `/v1/responses` |
> | reasoning effort | `none` (requested = effective) | `medium` (requested = effective) |
> | fixture | trivial-by-design 자작 3종 | nontrivial, clean/private |
> | 무엇을 판정하는가 | 도구 호출·상태 전파·telemetry·통합 비용·실행 안정성 | solve accuracy, time-to-flag, cost per solve, 장기 상태 유지 |
> | 무엇을 판정하지 **못하는가** | CTF 풀이 능력, 모델 선택, 최종 우승자 | — |
>
> **왜 지금 `none`인가.** `gpt-5.6-terra`는 `/v1/chat/completions`에서 function tools와
> reasoning_effort를 함께 받지 않는다. 여섯 칸을 실측했고 원본은
> `docs/spike/arms/T/capability-probes/openai-gpt-5.6-terra-chat-tools-effort-2026-08-07.json`
> 이다. **effort 부재도 실패한다.** T·E는 도구 계층이 곧 function calling이라 medium을
> 표현할 수 없고, X는 `wire_api=responses`라 가능하다. arm마다 다른 effort를 쓰면
> §9.6-2 위반이므로 전 arm을 `none`으로 맞춘다.
>
> **왜 지금 Responses로 이식하지 않는가.** T·E만 옮기면 tool 형식·`call_id` 연결·스트리밍
> 이벤트 모델·상태 유지·reasoning item 보존·캐싱·오류 경로가 동시에 바뀐다. URL 교체가
> 아니라 새 transport 구현이다. 더 중요한 것은 **Responses가 중립적 전송 계층이 아니라는
> 점**이다 — 같은 프롬프트·설정에서도 결과와 캐시 효율이 달라지므로, 한 arm만 옮기면
> **하니스 효과와 API 효과를 분리할 수 없다.** 이 스파이크가 재려는 것과 정반대다.
> 실무적으로도 T의 남은 구조 패치 예산 1개를 여기서 소진시킨다.
>
> **§9.6-1·§9.6-2에 걸리지 않는다.** 특정 arm을 살리려는 개정이 아니라 이 모델에서 그
> 조합이 **존재하지 않는다**는 API 제약이고, 전 arm에 같은 값을 쓴다. 결정 시점은 여섯 칸
> 관측 직후, **T의 seam 판정을 보기 전**이다.
>
> **결과를 부르는 이름에 제약이 붙는다.** endpoint가 arm마다 다르므로(T·E chat/completions,
> X responses) 이 스파이크의 산출물은 **"원형에 가까운 전체 OSS stack 비교
> (as-integrated system comparison)"**다. **"순수한 orchestration 품질 비교"나 "동일
> transport에서의 harness-only 비교"라고 부르면 안 된다.** 최종 후보끼리는 공통 Responses
> 어댑터 아래에서 transport-normalized 비교를 한 번 더 한다.
>
> **무결성 규칙 (계약에 넣는다).** 조용한 강등 금지 — 지원하지 않는 조합을 자동으로
> `none`으로 낮추지 않고, `requested_reasoning_effort != effective_reasoning_effort`이면
> **실행을 실패 처리한다.** effective effort는 선언이 아니라 관측이다
> (`usage.completion_tokens_details.reasoning_tokens`). 모든 run은 profile / provider /
> model_alias / **model_snapshot** / endpoint / requested·effective effort / tool_protocol /
> state_mode / store / streaming / capability_probe_id를 통제 블록에 기록한다.
>
> **후속 gate — foundation 채택 전 필수.** (1) shortlist 후보에 Responses transport 구현·검증,
> (2) 결선 후보 전부를 nontrivial clean fixture에서 **medium으로** 재평가, (3) solve rate·
> latency·cost·tool reliability·variance 비교, (4) **foundation-spike 결과만으로 승격하지
> 않는다.** 이 관문 전의 foundation 결정은 **provisional**이다.
>
> **대가:** 이 스파이크는 **어떤 arm도 medium에서 재지 않았다.** §12.2의 7번에 기재한다.

### 9.2 fixture 3종 — 자작, provenance `synthetic`

**이것들은 CTF 문제가 아니라 배관을 강제하는 계약 픽스처다.** 운영자 합의 2026-08-07로 용어를
"챌린지"에서 "fixture"로 바꾼다. 말이 바뀌면 저작 부담이 바뀌기 때문이다 — 필요한 것은 출제가 아니라
테스트 서버 작성이고, 세 개를 합쳐 수백 줄 규모다.

자작하는 이유는 세 가지다. (1) 합성이므로 `allow_vps=false` 호스트에서 처리 가능하다. (2) 오염과
holdout 문제가 발생하지 않는다. (3) **각 fixture를 우리가 시험하려는 seam만 정확히 때리도록 설계할 수
있다.** 공개 벤치마크는 이 세 가지를 모두 주지 못한다.

**fixture는 쉬워야 한다.** 난이도를 올리면 모델 능력이 배관 판정에 섞여 들어온다. 유형 B는 "어려워서
못 푼다"가 아니라 **"세션을 유지하지 못하면 절대 못 푼다"**여야 한다. 각 fixture는 **단일 경로**로
만든다 — 여러 경로를 열면 어느 seam이 통과했는지가 흐려진다.

**유형 A — 정적 분석.** 최소 요구: 아카이브 1개를 풀고, 그 안의 파일에 도구 2종(예: `strings`와 Python
한 조각)을 적용하고, **두 관찰을 합쳐야만** 얻어지는 값을 만든다. 어느 한 관찰만으로는 답이 나오지
않아야 한다. 큰 파일 1개를 넣어 S5의 절단·artifact 경로를 강제한다.

**유형 B — 인터랙티브 세션.** 최소 요구: 로컬 서비스에 붙은 뒤 **모델 턴을 최소 3회 가로질러** 같은
세션이 살아 있어야 답에 도달한다(예: 상태를 쌓아야 반응이 바뀌는 프로토콜, 또는 breakpoint 후에만
읽히는 값). 별도로 자식 프로세스를 만드는 명령을 포함시켜 timeout 후 프로세스 트리 정리(S2)를 관측한다.

**유형 C — 웹 상태.** 최소 요구: 로그인 → 세션 쿠키 획득 → 상태를 바꾸는 두 번째 요청 → 세 번째 요청에서
비로소 flag. **쿠키를 잃으면 반드시 실패**하도록 만든다. 동시 요청은 이 스파이크의 필수가 아니라
선택 변형으로 두고, 시도한 arm은 기록한다.

**공통 규칙:**
- 정답은 fixture 매니페스트 옆 호스트 파일에만 두고 **worker가 도달할 수 있는 어떤 경로에도 두지
  않는다.** `/input`, `/work`, fixture 서비스 응답 어디에도 없다. (S8, pack §9.2)
- fixture 서비스는 루프백 또는 호스트 내부 Docker 네트워크에서만 뜬다. 외부 노출 금지
  (`HOST_EXCEPTIONS.md` §6).

#### 9.2.1 fixture가 살아 있음의 증거 — 골든 트라젝토리

이전 판은 "사람이 손으로 5분 안에 푼 기록"을 요구했다. 목적은 하나였다 — **arm이 전부 실패했을 때
fixture 결함인지 arm 결함인지 가르는 것.** 그 목적을 스크립트로 달성한다(운영자 합의 2026-08-07).

fixture마다 **정답 경로를 스크립트로 함께 만든다.** 저작자가 아는 경로이므로 저작과 동시에 나온다.

제약 하나가 이 장치의 전부다: **골든 스크립트는 에이전트에게 노출된 도구 계층만 쓴다.** 정답을
하드코딩하거나 계약 밖의 지름길을 쓰면 확인이 무의미해진다. 계약 인터페이스로만 동작해야 하고,
그래서 이 스크립트는 사실상 **"완벽한 에이전트의 궤적"**이다.

사람 풀이보다 나은 점 셋:

1. **재현 가능하다.** 사람 풀이는 1회성이라 fixture가 나중에 망가져도 모른다. 스크립트는 **매 arm run
   직전에 돌려** fixture 건전성을 확인한다.
2. **검사기를 검증한다.** 골든 궤적을 흘렸을 때 해당 유형의 seam 술어가 전부 PASS여야 한다. 아니면
   술어가 틀린 것이다. 지금은 검사기를 검증할 수단이 없다.
3. **arm 실패를 진단한다.** 골든 궤적과 diff해 어디서 갈렸는지 본다.

**잃는 것, 명시.** 사람 풀이는 "저작자가 아닌 지능이 이걸 풀 수 있는가"를 확인하지만, 골든 스크립트는
**저작자가 의도한 경로가 작동한다**만 확인한다. fixture에 저작자가 못 본 결함이 있어 의도한 경로
외에는 아무것도 통하지 않는 경우를 잡지 못한다. 완화책은 위의 **단일 경로 설계**이며 손실을 작게
만들지만 0으로 만들지는 않는다. §12.2의 7번에 기재한다.

**fixture가 의도한 seam을 실제로 강제하는지**는 별도로 음성 프로브가 답한다 —
`SEAM_CONTRACT.md`의 S8-a(틀린 후보는 거부), S6-a/C-4(쿠키를 버리면 실패), B-9(세션을 끊으면 실패).
음성 프로브가 통과하면 fixture 검수가 끝난다. 사람 검수를 따로 두지 않는다.

골든 스크립트마저 실패하면 **그때는 사람이 본다.** 그 시점에는 어차피 사람이 봐야 한다.

### 9.3 판정 규칙

각 (arm × 유형)에 대해 seam별로 하나만 부여한다.

- **PASS** — 통과. 구조 패치 없음.
- **PASS(patch n)** — 통과하되 구조 패치 n개 필요.
- **FAIL(Sk)** — seam k에서 막힘.
- **N/A** — 그 유형이 그 seam에 하중을 싣지 않음(§4).

**구조 패치**의 정의: 후보의 core loop, 상태 모델, 도구 인터페이스, 격리 모델을 바꾸는 변경.
**사소 패치**: pin, packaging, import 경로, 문서 오류, 명백한 버그 수정. 사소 패치는 개수 제한이 없되
전부 diff와 이유를 기록한다.

**패치 예산: 후보당 구조 패치 3개** [pack §10 Stage 1]. 4번째가 필요하면 그 후보의 해당 유형은
FAIL이고, 스파이크를 계속하지 않는다.

### 9.4 arm마다 기록해야 할 것

`PINS.md`(repo, commit, submodule, image digest), `LICENSE_MATRIX.md`(라이선스, 제품 사용 가부, 고지
의무, copyleft/network 조항, 확인한 원문 위치), `REPRO_MATRIX.md`(clean build, smoke, headless, 로그

```
flag 후보와 그 출처 관찰 id / verifier 판정
모델 호출 수 / 입력·캐시·출력 토큰 / USD
web search 사용 여부와 질의 원문 (EVAL_CONTRACT: 차단이 아니라 기록)
```

### 9.5 비용과 상한

`config/pricing.openai.yaml`의 `gpt-5.6-terra` 단가로 계산한다. **아래는 가정을 대입한 산술이지
측정값이 아니다.** 첫 run 이후 실측으로 대체한다.

가정: run당 모델 호출 20회, 호출당 입력 60K(캐시 적중 90%), 출력 2K.

```
입력  20 × (6K × $2.00/M + 54K × $0.20/M) = 20 × $0.0228 = $0.456
출력  20 × 2K × $12.00/M                                  = $0.480
run 1회 ≈ $0.94
모델 구동 arm 3(T·E·X) × 유형 3 × 반복 2 = 18 run ≈ $17
디버깅·재시도 3배 마진                        ≈ $51
```

G는 스크립트 드라이버로 도는 참조 구현이므로 이 예산에 들어가지 않는다(§9.1).

**하드 캡 $150 — 단, 관측되는 값이지 강제되는 값이 아니다.** 운영자 결정 2026-08-07로 전용 키 대신
기존 키를 재사용하므로(`HOST_EXCEPTIONS.md` §7), provider 예산이 대신 잘라 주지 않는다. 상한은
**매 arm run 후와 매 세션 경계에서 사람이 대조해야** 지켜진다. 기록된 `usd` 합계만 보면 후보가 우리
telemetry 밖에서 호출한 분이 빠지므로, provider 콘솔의 사용량을 함께 본다. 초과하면 스파이크를
중단하고 그 시점까지의 판정표로 §12를 채운다. 캐시 적중 90%는
가정이며, 실측 6회에서 `cached + cache_write + 3 == input`이 성립한 기록이 있다 [ev §5]. 272K를
넘기면 전 요청이 2배로 재과금되므로, 넘긴 run은 비용이 아니라 **S5/S6 부적합 신호**로 먼저 읽는다.

### 9.6 스파이크를 무효로 만드는 것

[pack §13]을 이 스파이크에 맞춰 좁힌 것이다.

1. 특정 arm을 살리려고 챌린지, timeout, 계약, 판정 기준을 바꾸는 것. 바꿔야 한다면 새 experiment ID를
   만들고 이전 결과는 폐기한다.
2. arm마다 다른 모델·다른 예산·다른 verifier를 쓰는 것.
3. 구조 패치를 사소 패치로 분류하는 것.
4. 실패한 arm의 trace를 지우는 것. 실패 trace와 폐기 이유는 보존한다.
5. 사람이 중간에 개입하고 그 사실을 기록하지 않는 것.
6. 결과를 본 뒤 §10의 결정 규칙을 고치는 것.

### 9.7 실행 순서와, 시간이 모자랄 때 자르는 순서

운영자 합의 2026-08-07. **순서는 판정 기준이 아니라 정보 획득 효율의 문제**이므로 여기서 정해도
§9.6-1에 걸리지 않는다. 다만 결과를 본 뒤에 바꾸면 걸린다.

**실행 순서**

2. 유형 B. 판별자이므로 여기에 시간을 쓴다.
3. 유형 C.

**범위를 줄여야 할 때 자르는 순서**

## 10. 사전 등록된 결정 규칙

**결과를 보기 전에 확정한다.** 이것이 이 문서의 존재 이유다. 2026-08-07에 운영자 합의로 한 차례
개정했고, 개정 이유는 §10.4에 남긴다. **첫 run 이후에는 고치지 않는다**(§9.6-6).

### 10.1 각 선택지의 생존 조건

독립적으로 평가한다. 서로 겹치지 않는다.

| 선택지 | 생존 조건 |
|---|---|
| 1 OSS fork | T가 유형 A·B·C **전부**를 구조 패치 3개 이하로 통과 |
| 2 component extraction | 어떤 seam에서 E가 §3 계약 뒤에서 구조 패치 3개 이하로 통과. 생존 범위는 **그 seam에 한정** |
| 3 greenfield | G가 `SEAM_CONTRACT.md` §4.1의 네 요구와 유형 B 프로브 B-1~B-8을 **전부** 통과 |

선택지 2의 생존은 선택지 3의 생사와 무관하다. G가 죽었다는 것은 우리가 세션 런타임을 못 만든다는
뜻이고, 선택지 2에서는 그 자리를 E가 채우며 나머지 seam은 §7.2에서 낮음·중간으로 판정한 것들이다.

### 10.2 선택

- **생존 0개** → foundation을 고르지 않는다. 그 seam이 왜 통과 불가였는지를 먼저 규명한다. 결론은
  "선택지 없음"이며, 셋 중 하나를 억지로 고르는 것보다 낫다.
- **생존 1개** → 그것.
- **생존 복수** → 기본 순서는 **1 > 2 > 3**. 근거는 §10.4.
- **한 가지 예외** → 선택지 2와 3이 함께 생존했고, **유형 B의 세션 런타임이라는 동일 범위에서**
  G의 참조 구현 작성 시간이 E의 구조 패치 작성 시간보다 작으면, **3이 2보다 앞선다.**
  선택지 1은 이 예외의 대상이 아니다(§10.4).
- **같은 선택지 안에 후보가 둘 이상일 때** → 구조 패치 수 → S9 telemetry 적합성 → 라이선스 위험 →
  운영 복잡도.

### 10.3 선택지 1을 고른 경우의 후속 의무

§5.1의 일곱 가정 중 무엇을 즉시 교체하고 무엇을 안고 갈지 §13에 명시한다. 4(느슨한 성공 판정)는
교체가 선택이 아니다 — `EVAL_CONTRACT.md`와 정면으로 충돌한다.

### 10.4 이 규칙이 2026-08-07에 바뀐 이유

**폐기한 것 1: 이전 판의 규칙 5** ("T와 G가 모두 통과하면 선택지 3 우선"). 근거가 "같은 seam
결과라면 fork가 물려주는 가정이 순수한 부채"였는데, G를 §4 참조 구현으로 좁히면서 **그 전제가
성립하지 않게 되었다.** T의 통과는 9 seam × 3 유형에 대한 측정이고 G의 통과는 유형 B의 세션 술어에
대한 측정이다. 같은 범위를 재지 않으므로 "같은 seam 결과"라는 조건이 만족될 수 없다.

**폐기한 것 2: 이전 판 규칙 3의 비용 비교** ("T·E의 통과 비용(구조 패치 수)이 G보다 크다"). G는 우리
코드라 구조 패치가 없다. 구조 패치 수와 구현 시간은 단위가 달라 비교가 **정의되지 않았다.** §10.2의
예외는 이것을 정의 가능한 형태로 되살린 것이다 — 범위를 유형 B의 세션 런타임으로 맞추고, 단위를
양쪽 다 작성 시간으로 통일했다. 그래서 §9.4에 시간 기록이 추가되었다.

**기본 순서를 1 > 2 > 3으로 둔 근거.** 두 축이 충돌한다.

- 물려받는 부채의 양: 3 < 2 < 1 (§7.1 < §6.1 < §5.1)
- 측정된 증거의 양: 1 > 2 > 3

**측정된 증거를 우선한다.** 이 문서는 명성·코드량·논문 점수를 근거에서 빼고 측정만 근거로 삼겠다고
선언했다. 그래 놓고 측정 범위가 가장 좁은 쪽을 우선하면 자기모순이다. 부채는 §10.3의 후속 의무로
관리할 수 있고, 측정 공백은 관리할 수 없다. §10.2의 예외가 좁게 걸린 것도 같은 이유다 — 그 예외는
범위가 실제로 겹치는 한 지점에서만 발동한다.

### 10.5 사전 등록된 우발 조항

대조군 **X(Codex CLI)가 얇은 wrapper만으로 A·B·C를 전부 통과하면**, 그 사실을 §12에 기록하고
**선택지 집합을 다시 연다.** "범용 CLI agent를 wrap한다"는 이 문서가 검토하지 않은 네 번째
선택지이며, 그 경우 §10.1~10.3은 적용하지 않고 별도 검토를 연다. 결과를 보고 규칙을 고치는 것이
아니라, 그 가능성을 미리 적어 두는 것이다.

X가 §9.7에 따라 잘린 경우, 이 조항은 발동할 수 없다. 그 사실을 §12에 적는다.

## 11. 잠정 가설 (근거 없음, 결정 아님)

이것은 예측이며 §12를 채우는 데 쓸 수 없다. 스파이크가 반증할 대상으로만 적는다.

- 유형 A는 네 arm 모두 통과할 것이다. 따라서 A는 후보를 가르지 못한다.
- 유형 B에서 T가 구조 패치 3개 안에 들어오지 못할 가능성이 가장 높다. 근거: D-CIPHER 계열이 interactive
  interface를 구현하지 않았다는 논문 자신의 진술 [pack §5.2].
- 유형 C는 네 arm 모두 쿠키·세션 유지까지는 통과하고, 브라우저/JS가 필요한 변형에서 전부 막힐 것이다.
  그렇다면 유형 C는 선택지를 가르지 못하고 **공통 미해결 항목**으로 §13에 넘어간다.
- 가장 가능성 높은 결과는 **선택지 2 단독 생존**, 즉 "전체 포크는 아니고 B의 런타임만 추출"이다.

이 넷 중 하나라도 맞았다는 사실은 결정의 근거가 아니다. 판정표가 근거다.

## 13. 결정 이후에 쓸 문서의 범위

결정 전에는 쓰지 않는다 [pack §13 규칙 10]. 순서는 **결정 → 아래 문서들 → 재빌드**이고, 운영자
계획의 3번 단계에 해당한다.

### 13.0 누가 언제 쓰는가

네 단계는 서로 다른 세션이고, 순서대로 진행한다. 앞 단계가 끝나기 전에 다음 단계를 시작하지 않는다.

| 단계 | 하는 일 | 산출 |
|---|---|---|
| **스파이크 세션** | §9 실행 | `PINS.md`, `LICENSE_MATRIX.md`, `REPRO_MATRIX.md`, §12.1 판정표 |
| **결정** | §10.1의 생존 판정 → §10.2 적용 | §12 기재. 사람이 한다 |
| **문서 세션** | §13.1 전부 작성 | `spec.md`, telemetry 스키마, `CLAUDE.md`, 경로 스코프 규칙, holdout 봉인 |
| **재빌드 세션** | 코드 | 위 문서를 **따른다. 쓰지 않는다** |

**재빌드 세션은 §13.1의 문서를 작성하지도 고치지도 않는다.** 고쳐야 한다고 판단되면 멈추고 보고한다.
이 규칙이 없으면 재빌드가 진행되면서 spec이 코드에 맞춰 사후 수정되고, 사전 등록의 의미가 사라진다 —
이 문서 전체가 막으려는 실패다.

문서 작업은 재빌드 세션의 일이 아니다. 아래 일곱 항목이 전부 끝난 뒤에 재빌드가 시작된다.

### 13.1 재빌드 전에 반드시 쓰는 것

1. **§3 계약의 확정판** = `spec.md`의 뼈대. seam별 통과 조건과, 교체 가능 지점의 인터페이스. 구현
   무관. `SEAM_CONTRACT.md` 초안을 스파이크 결과로 고쳐 승격시킨다.
2. 선택된 선택지와 그 근거로 쓰인 판정표의 위치. 선택지 1이면 §10.3의 후속 의무도 여기에.
3. 어떤 seam이 어떤 구현으로 채워지는가의 대응표(자작 / vendored / fork 내부).
4. `EVAL_CONTRACT.md`를 만족하는 telemetry 스키마 = `SEAM_CONTRACT.md` §1의 확정판.
   추가로 **§13.1.a의 두 소비자를 먹일 수 있어야 한다** — 라이트업 충분성과 escalation 패킷 충분성.
   세션 C의 `S9-SUFFICIENCY` 점검 결과와 그것이 남긴 공백을 반영한다.
5. **`CLAUDE.md`** — 재빌드 세션이 **따를** 작업 규약. 재빌드 세션이 쓰는 것이 아니다(§13.0).
   결정보다 먼저 쓰지 않는 이유는 [pack §13 규칙 10] — 정당화된 적 없는 아키텍처에 독자를 묶게 된다.
   그래서 결정 뒤, 재빌드 앞이라는 좁은 자리에 온다.
6. **경로 스코프 규칙** — 무엇을 어디에 두고, 실행 주체가 어느 경로를 만질 수 있는가. 대부분 이미
   쓴 것에서 유도된다: 컨테이너 쪽은 `SEAM_CONTRACT.md` S2의 마운트 술어와 `SAFETY_SCOPE.md`,
   호스트 쪽은 `HOST_EXCEPTIONS.md` §4~5의 경로 분리.
7. **holdout 봉인** — 챌린지 세트를 dev / regression-private / final-holdout으로 **가르고 봉인만**
   한다. 근거: `EVAL_CONTRACT.md`가 "사람이 에이전트를 고치려고 들여다본 챌린지는 holdout에서
   나간다"고 규정하므로, 재빌드 중에 보게 될 챌린지는 전부 holdout 자격을 잃는다. 재빌드 뒤에 가르면
   이미 오염된 뒤다. **되돌릴 수 없는 것은 이 한 가지뿐이라 이것만 앞에 온다.**

### 13.1.a 프로덕션은 하나다 — 라이트업과 escalation은 그 하나의 계층

운영자 결정 2026-08-07. **제품은 하나이고, 그 목표는 대회 성적이다.** 아래 둘은 별도 제품이 아니라
그 하나의 제품이 가진 두 계층이며, 둘 다 seam이 아니라 **S9(telemetry)의 소비자**다. 계층을 쌓는
순서만 정해져 있다: escalation은 "막힌 문제를 넘긴다"이므로 넘길 대상인 **자율 코어가 먼저** 있어야
얹힌다. 그래서 재빌드 후에 오며, 별도 제품이라서가 아니다.

**지표의 위치를 여기서 못 박는다.**

- `clean_solve@1` — 목표가 아니라 **도구**다. foundation을 고르고 자율 코어가 나아지는지 재는,
  오염되지 않은 유일한 자다. 사람·타 모델이 섞이면 arm에 능력을 귀속시킬 수 없으므로 스파이크와
  foundation 결정은 이 숫자로 한다. 없애지 않는다.
- `contest_solve` — **실제 목표.** escalation 보조(사람 매개 + 멀티모델 + 재주입)를 포함한 성적.
- **후자는 전자를 대체하지 않는다.** `EVAL_CONTRACT.md`가 solve@k에 이미 건 규칙과 동형이다.

`OBJECTIVE.md`는 바꾸지 않는다. 그 문서는 "autonomously ... produces a verified flag"로 자율 코어를
규정하며, escalation은 그 위에 얹히는 하류 능력이라 OBJECTIVE 하위에 놓인다.

**문서 세션이 이 절 때문에 반드시 하는 것:**

1. **두 소비자를 재빌드 산출물로 명명한다** — 라이트업 생성기, escalation 패킷 컴파일러. 어느 것도
   seam이 아니다. 둘 다 telemetry의 투영이다. 라이트업 소재는 §13.1-4의 스키마가, 패킷 소재도 같은
   스키마가 나른다.
2. **telemetry 스키마에 예약 필드를 둔다** — `hypothesis.recorded` / `hypothesis.rejected`, 그리고
   stall 신호(confirmed-fact 표시, attempt-family, confidence). 단일 경로 fixture는 이것을 행사하지
   못해 스파이크에서 검증되지 않지만, 계약이 언 뒤에 넣는 비용이 seam-first 규칙이 존재하는 이유다.
   세션 C가 `CHECKER.md`에 이 공백을 이미 기록해 둔다.
3. **canon 두 곳을 편집한다(서명 필요, 지금이 아니라 문서 세션에서).**
   - `SAFETY_SCOPE.md`: escalation egress 예외. 챌린지 유래 콘텐츠는 **하나의 게이트된, 비밀
     제거된, scope 검사된 export**를 통해서만 외부 모델로 건너간다. 그 egress 자체가 "호스트 egress =
     `api.openai.com` 단독"의 예외다. **지금 넣지 않는 이유:** escalation은 재빌드 후에야 작동하므로
     이 egress가 지금 필요 없고, "결정 전 canon 재작성 금지"에도 맞는다.
   - `EVAL_CONTRACT.md`: 위의 `contest_solve` vs `clean_solve@1` 구분을 명문화.
4. **escalation 설계의 나머지**(blind independent analysis, verifier-only 성공 판정, scope gate, secret
   scrubbing, stall 트리거, 격리 실행)는 재빌드 이후 escalation 계층의 명세로 넘긴다. 이 문서는 그
   계층이 **어느 seam에 요구를 거는지**(S9 소비, S2 export 경계, S6 재주입)만 고정한다.

### 13.2 재빌드 뒤로 미루는 것

**성능 단계의 나머지 전부** — 반복 수, anti-cheat 감사 절차, 지표 파이프라인, clean_solve@1 · p95 ·
cost의 실제 측정. 세트가 봉인되어 있는 한 이것들은 나중에 정해도 늦지 않고, 재빌드 전에 정하면
아직 존재하지 않는 것에 맞춰 정하게 된다. (운영자 합의 2026-08-07: 이전 판은 성능 단계 진입 조건
전체를 재빌드 앞에 두었고, 그것은 과했다.)

### 13.3 이 문서가 정하지 않은 채로 남기는 것

다음 문서로 넘어가는 질문:

- agent loop의 형태(단일 executor / 선택적 planner / 상시 planner)
- 모델 라우팅. **escalation은 §13.1.a에서 채택이 정해졌고**, 그 계층의 상세 설계만 재빌드 이후로 남는다
- 디렉터리 구조와 모듈 경계
- **현 프로토타입 코드의 재사용 여부.** §7.1에 적은 대로 이 질문은 foundation 선택과 독립이고,
  선택 후에 seam 단위로 `docs/evidence/2026-08-07-phase-b-evidence.md`를 근거로만 판단한다
- 유형 C의 브라우저/JS 실행과 동시성 — §11이 맞다면 이건 선택지가 아니라 공통 미해결 항목이다
