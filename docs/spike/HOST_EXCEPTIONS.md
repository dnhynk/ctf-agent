# HOST_EXCEPTIONS — foundation spike를 기존 호스트에서 돌리기 위한 승인 요청

작성일 2026-08-07. 상태: **승인됨 (2026-08-07, dnhynk). 만료 2026-08-21.**
`docs/canon/SAFETY_SCOPE.md`의 "Time-limited exception: OSS foundation spike" 절에 반영되었다.
스파이크 착수 시 §10에 착수일을 기록하고, 종료·만료 시 §9 체크리스트를 실행한다.

`docs/spike/FOUNDATION_DECISION.md` §9의 스파이크를 `203.0.113.10`(제품 통합 호스트)에서 실행하기로
운영자가 결정했다(2026-08-07). `docs/canon/SAFETY_SCOPE.md`는 canon이고 "여기서 허용하지 않은 것은,
그것을 할 수 있는 코드가 있든 없든 scope 밖"이라고 규정한다. 아래 항목 중 일부는 그 문서를 그대로
두면 스파이크가 위반하게 되는 것들이다.

**이 문서는 canon을 고치지 않는다.** 무엇이 필요한지, 왜 필요한지, 무엇으로 범위를 좁혔는지, 어떻게
회수하는지를 적고 운영자 승인을 요청한다. 승인되면 `SAFETY_SCOPE.md`에 기간 한정 예외로 반영하는 것이
운영자의 몫이다.

**스파이크 세션**(§9를 실행하는 세션. `FOUNDATION_DECISION.md` §13.0의 네 단계 중 첫째)이 이 문서를
읽지 않고 호스트를 만지면 안 되는 이유는 §5와 §7이다.

## 1. 챌린지 provenance — 예외 불필요 (설계로 회피)

호스트는 `deployment_class=vps`이고 `allow_vps=false`다. 따라서 대회 유래 입력의 반입·저장·실행은
거부된다 [`SAFETY_SCOPE.md`, `docs/evidence/2026-08-07-phase-b-evidence.md` §2].

스파이크는 자작 합성 fixture 3종만 쓴다(`FOUNDATION_DECISION.md` §9.2). `provenance: synthetic`이므로
게이트에 걸리지 않는다. **`allow_vps` 변경을 요청하지 않는다.**

**금지:** NYU CTF Bench, XBOW validation-benchmarks, CyBench, InterCode, picoCTF 아카이브를 이 호스트에
반입하지 않는다. 후보 하니스가 자기 벤치마크 데이터를 함께 받아오는 경우, 해당 데이터 디렉터리를
받지 않거나 즉시 삭제하고 그 사실을 기록한다. 공개 벤치마크가 필요해지는 시점은 성능 단계이고, 그때
`allow_vps`를 별도로 결정한다.

## 2. Docker 소켓 — **예외 필요**

`SAFETY_SCOPE.md`는 Docker 소켓을 명시적으로 scope 밖에 둔다. 그러나 후보 하니스(TATAR, EnIGMA)는
자기 컨테이너를 스스로 만든다. `/dev/kvm`이 없으므로 VM 격리로 우회할 수 없다.

**요청:** 스파이크 전용 계정에 한해, 기간 한정으로 Docker 소켓 접근을 허용한다.

**범위를 좁히는 방법:**
- 스파이크 전용 비특권 사용자(예: `ctf-spike-user`)를 새로 만들고 그 사용자만 `docker` 그룹에 넣는다.
  서비스 계정 `ctf`의 권한을 늘리지 않는다.
- 소켓을 **후보 컨테이너 안으로 마운트하지 않는다.** 후보 하니스는 호스트에서 실행하고 컨테이너를
  만들게 하되, 그 하니스가 만든 컨테이너에 소켓을 다시 넣는 구성(중첩 제어)은 거부한다.
- 후보가 소켓 마운트를 요구하면 그것을 **구조 패치이자 관측치**로 기록한다
  (`FOUNDATION_DECISION.md` §9.3).

**회수:** 스파이크 종료 시 `ctf-spike-user` 사용자를 `docker` 그룹에서 제거하고 계정을 삭제한다.

**감수하는 위험(명시):** 소켓 접근은 사실상 호스트 root와 동등하다. 스파이크 기간 동안 이 호스트는
"미검증 OSS 코드가 root 동등 권한으로 도는 기계"로 간주해야 한다. 그래서 §7(키)과 §4(데이터)의 분리가
선택이 아니라 필수다.

## 3. egress — **예외 필요**

현재 허용은 `api.openai.com` 단독이다.

**요청:** 아래 목적지로 한정해 임시 허용.

| 목적지 | 이유 |
|---|---|
| `api.openai.com` | 기존 허용. 모델 호출 |
| `github.com`, `codeload.github.com`, `objects.githubusercontent.com` | 후보 저장소 clone |
| `registry-1.docker.io`, `auth.docker.io`, `production.cloudflare.docker.com` | 베이스 이미지 pull |
| `ghcr.io`, `pkg-containers.githubusercontent.com` | 후보가 GHCR 이미지를 쓰는 경우 |
| `pypi.org`, `files.pythonhosted.org` | 후보 의존성 |
| 배포판 패키지 미러 (Debian/Ubuntu/Kali 중 실제로 쓰는 것) | 이미지 빌드 |

**규칙:**
- 실제로 필요해진 시점에 하나씩 추가하고, 추가할 때마다 이유와 날짜를 이 문서 §10에 적는다.
- 미리 넓게 열지 않는다. `0.0.0.0/0` 허용 금지.
- **스파이크가 도구 실행 중 임의 egress를 필요로 하는 경우, 그것은 seam 관측이지 정책 요청이 아니다.**
  자작 챌린지는 전부 호스트 내부에서 완결되므로, worker가 외부로 나가야 한다는 것은 후보 하니스가
  네트워크 정책을 강제하지 못한다는 증거다(S2 FAIL).
- 후보 하니스의 web search 도구는 차단하지 않고 **기록한다**. `EVAL_CONTRACT.md`가 검색으로 얻은 flag를
  실패로 규정하므로, 차단해 버리면 그 행동을 관측할 기회를 잃는다.

**회수:** 스파이크 종료 시 추가한 규칙을 전부 제거하고 `api.openai.com` 단독으로 되돌린다. §9에서
확인한다.

## 4. 디스크와 데이터 분리 — **예외 아님, 운영 규칙**

320 GiB를 프로토타입 데이터와 공유한다. Kali 계열 이미지와 후보별 컨테이너는 수십 GiB가 될 수 있다.

- 스파이크 산출물은 `<HOME>/` 아래에만 둔다. `<PROTO_HOME>/kisia-data`를 쓰지 않는다.
- **`<PROTO_HOME>/kisia-data`의 이벤트 로그를 삭제하지 않는다.** `events-000001.jsonl`은
  `docs/evidence/2026-08-07-phase-b-evidence.md` §5가 인용하는 유일한 실측 기록이고, 재생성할 수 없다.
- `config/images.lock.yaml`에 digest로 고정된 6개 프로토타입 이미지를 삭제하지 않는다. 같은 이유다.
- 디스크 사용률 80%에서 스파이크를 멈추고 정리한다. 남은 공간을 프로토타입 데이터 삭제로 확보하지
  않는다.
- 각 arm 종료 시 `docker system prune`은 **스파이크 이미지에 한정된 필터로만** 실행한다. 무필터 prune
  금지.

## 5. 제품 checkout 불변 — **절대 규칙**

`<PROTO_HOME>/kisia-agent`(그리고 그 안의 git 상태)는 스파이크가 건드리지 않는다.
[pack §10 Stage 0 규칙 1, §13 규칙 9] 스파이크는 `<HOME>/` 아래 별도 checkout에서 돈다.

이 문서와 `FOUNDATION_DECISION.md`는 Windows 워크스페이스에서 작성해 커밋하는 것이고, 호스트의
제품 checkout을 수정해도 된다는 뜻이 아니다.

## 6. 방화벽과 챌린지 서비스 노출 — **예외 아님, 금지 사항**

- 자작 챌린지 서비스(유형 B의 소켓, 유형 C의 웹 앱)는 **루프백 또는 호스트 내부 Docker 네트워크에서만**
  뜬다. `-p 0.0.0.0:...` 형태의 퍼블리시 금지.
- `ufw` 기본 정책을 바꾸지 않는다. 22/tcp 외 어떤 포트도 공중에 열지 않는다.
- `ufw`를 만질 일이 생기면 `docs/runbook/ssh-and-firewall.md`의 절차를 그대로 따른다. 스파이크 편의를
  위해 절차를 건너뛰지 않는다. `ufw disable` 금지.
- 후보 하니스가 챌린지 서비스를 자동으로 퍼블리시하는 경우, 그 동작을 막고 **구조 패치로 기록**한다.

## 7. API 키 — **분리 필수**

현재 키는 `<PROTO_HOME>/.config/kisia-agent/secrets.env`(0600, `ctf:ctf`)에 있다.

**운영자 결정 2026-08-07: 기존 키를 재사용한다.** 같은 날 앞서 승인된 "전용 키 발급" 요구를 대체한다.

이 절은 그 결정을 기록하고, 그 결정으로 **잃는 통제와 그것을 대신하는 장치**를 정한다.

### 7.1 잃는 것 — 완화하지 않고 감수한다

1. **$150 상한이 provider에서 강제되지 않는다.** 전용 프로젝트에 예산을 걸었다면 provider가 잘라
   줬겠지만, 공용 키에는 그 장치가 없다. 상한은 이제 **관측되는 값이지 강제되는 값이 아니다**
   (`FOUNDATION_DECISION.md` §9.5).
2. **유출 시 폐기 대상이 제품 키다.** 전용 키였다면 폐기 하나로 끝났다. 이제 유출은
   `~/.config/kisia-agent/secrets.env`의 교체를 뜻하고, 그 경로는 §5가 스파이크에게 금지한 곳이다.
   교체는 운영자가 한다.

이 둘은 감수한 위험이며, 아래 장치는 위험을 없애지 않고 **빨리 발견**하기 위한 것이다.

### 7.2 대신 반드시 하는 것

- **키는 프로세스 환경변수로만 후보에게 간다.** `<HOME>` 아래 어떤 파일에도 쓰지 않고,
  컨테이너 안에 넣지 않고, 프롬프트에 넣지 않는다.
- **매 arm run이 끝날 때마다 그 arm의 로그·trace·artifact를 키 문자열로 검색한다.**
  후보 코드가 키를 어디에 남기는지 우리는 모른다. 이것이 그것을 알아내는 유일한 장치다.
  적중하면 **스파이크를 멈추고**, 운영자에게 보고하고, 키를 교체한 뒤에만 재개한다. 적중 사실과
  어느 후보의 어느 파일이었는지를 기록한다.
- **매 arm run 후와 매 세션 경계에서 누적 비용을 $150 상한과 대조한다.** 기록된 `usd` 합계와
  provider 콘솔의 사용량을 둘 다 본다. 기록만 보면 후보가 우리 telemetry 밖에서 호출한 분이 빠진다.
- 후보 하니스가 **컨테이너 안에서** 모델을 호출해야만 동작한다면, 키를 컨테이너에 넣지 말고 그 요구를
  구조 패치이자 관측치로 기록한다.
- `~/.config/kisia-agent/secrets.env` 파일 자체를 후보에게 마운트하거나 읽게 하지 않는다.
  값만 환경변수로 전달한다.

### 7.3 Windows 워크스페이스의 `.env`

확인 2026-08-07: `.gitignore` 2행에 잡혀 있고 git에 추적되거나 커밋된 적이 없다. 스파이크는 호스트에서
돌므로 이 파일을 쓰지 않는다. 호스트로 복사하지 않는다.

## 8. 기간

### 8.1 만료

스파이크 착수일부터 **14일**. 착수일을 §10에 기록하지 않으면 승인일 기준으로 계산한다. 두 값 중
이른 쪽이 만료일이며, **승인일 2026-08-07 기준으로 만료는 2026-08-21**이다.

초과 시 예외는 자동 만료로 간주한다. 연장하려면 이 문서에 연장 사유와 날짜를 추가해 다시 승인받고,
`SAFETY_SCOPE.md`의 예외 절에 있는 만료일도 함께 고친다. 만료 시점에 §9.2를 실행한다.

### 8.2 14일은 노출 상한이지 작업 추정치가 아니다

이 숫자는 "미검증 OSS가 root 동등 권한으로 도는 기계를 얼마나 오래 열어둘 것인가"에서 나왔다. 일이
얼마나 걸리는지에서 나오지 않았다. **만료일은 상한이며 하한이 아니다.** 일이 사흘에 끝나면 사흘째에
§9.2를 실행하고 닫는다. 창이 열려 있는 동안은 그 호스트가 계속 노출 상태이므로, 일찍 닫는 것이 언제나
낫다.

작업량 추정은 세션 A의 boot smoke가 끝난 뒤에 처음으로 근거를 갖는다. 그 전에 일정을 약속하지 않는다.

### 8.3 세션 간 휴면

작업은 연속되지 않는다. **다음 작업 세션까지 하루 이상 간격이 예상되면 §9.1을 실행해 휴면으로
돌린다.** 재개할 때 되살린다. 창을 14일 내내 열어 두는 것과 실제 작업일만 여는 것은 실효 노출 시간이
크게 다르고, 되돌리는 비용은 명령 두어 개다.

열고 닫은 시각을 §10에 매번 기록한다. 그래야 스파이크가 끝난 뒤 **실효 노출이 며칠이었는지**를 말할
수 있다. 만료일까지 남은 일수와 실효 노출은 다른 값이다.

## 9. 회수

두 가지가 있다. §9.1은 되돌릴 수 있고, §9.2는 되돌리지 않는다.

### 9.1 휴면 — 작업 세션 사이 (§8.3)

```
휴면으로 돌릴 때
[ ] ctf-spike-user 사용자를 docker 그룹에서 제거 (계정과 <HOME> 는 유지)
[ ] 스파이크가 만든 컨테이너를 정지 (삭제하지 않는다. 재개 시 다시 쓴다)
[ ] §3에서 추가한 egress 규칙이 네트워크 계층에 실재한다면 제거
[ ] 그 세션에서 돈 arm의 로그·trace·artifact를 키 문자열로 검색 (§7.2). 적중 시 즉시 보고
[ ] 누적 비용을 $150 상한과 대조 (기록 + provider 콘솔 양쪽)
[ ] 휴면 시각을 §10에 기록

재개할 때
[ ] ctf-spike-user 사용자를 docker 그룹에 재추가
[ ] 필요한 egress 규칙만 다시 추가
[ ] 재개 시각을 §10에 기록
[ ] 만료일(§8.1)이 지나지 않았음을 확인. 지났으면 재개하지 말고 재승인을 받는다
```

### 9.2 종료 회수 — 스파이크 종료 또는 만료 시 (전부 실행하고 결과를 기록)

```
[ ] ctf-spike-user 사용자를 docker 그룹에서 제거하고 계정 삭제
[ ] §3에서 추가한 egress 규칙 전부 제거, api.openai.com 단독으로 복귀했음을 확인
[ ] <HOME> 전체를 키 문자열로 검색해 0건임을 확인 (§7.2)
[ ] 스파이크가 만든 컨테이너 이미지·볼륨에 키가 굳어 들어가지 않았는지 확인
[ ] provider 콘솔의 총 사용량을 기록하고 $150 상한과 대조
[ ] 키 교체 여부 판단: 위 검색이 한 번이라도 적중했다면 교체한다. 판단과 근거를 §10에 남긴다
[ ] <HOME> 삭제
[ ] 스파이크가 만든 컨테이너·이미지·볼륨·네트워크 0 잔존 확인
[ ] <PROTO_HOME>/kisia-data 와 프로토타입 이미지 6개가 그대로 있음을 확인
```

### 10.2 §3(egress)이 실행 없이 닫힌 이유 — 관측

세션 A가 §3을 실행하기 전에 "호스트 egress가 실제로 무엇으로 강제되는가"를 관측했다. 결과:

```
/etc/default/ufw : DEFAULT_OUTPUT_POLICY="ACCEPT"
iptables -S OUTPUT: -P OUTPUT ACCEPT (ufw-user-output 체인에 규칙 0개)
연결 시험 443/tcp : github.com OK / registry-1.docker.io OK / pypi.org OK / api.openai.com OK
ufw status       : inbound 22/tcp from 198.51.100.20 한 줄이 전부
```

**호스트 outbound는 네트워크 계층에서 전혀 제한되지 않는다.** `SAFETY_SCOPE.md`의
"Host egress: `api.openai.com` only"는 **코드에 관한 서술**이었다 — 같은 줄이 근거로 드는 것이
"`httpx`가 OpenAI 어댑터에만 있다"이고, 그것은 우리 코드가 어디로 나가는지에 대한 진술이지 호스트가
어디로 나갈 수 있는지에 대한 진술이 아니다. 이 구분은 이 세션 전에 확인된 적이 없다.

그 결과 §3은 **추가할 규칙이 0개**다. 열려고 한 것이 이미 전부 열려 있다. 따라서:

- §9.1의 "추가한 egress 규칙 제거"와 §9.2의 "추가 규칙 전부 제거, `api.openai.com` 단독 복귀"는
  **"추가한 것 없음"으로 닫힌다.** 복귀시킬 상태가 존재하지 않는다.
- §3의 표는 정책 기록으로 남는다. 어느 목적지를 썼는지는 아래 세션별로 적는다.
- **감수하는 위험이 §2의 서술보다 크다.** §2는 소켓 접근을 근거로 "이 호스트는 미검증 OSS가 root
  동등 권한으로 도는 기계"라고 적었는데, 여기에 **egress 무제한**이 더해진다. 후보 하니스가 어디로
  나가든 네트워크가 막지 않는다. §7.2의 키 검색이 이 조합에서 유일한 탐지 장치라는 뜻이고, 그래서
  세션 A는 그것을 Stage 0에서 한 번 실제로 돌려 작동을 확인한다.
- 이 사실은 canon의 서술과 네트워크 사실의 괴리이므로 스파이크 종료 후 `SAFETY_SCOPE.md`의
  "Allowed network" 표를 고칠지 여부가 별도 판단 대상이다. **세션 A는 canon을 고치지 않는다.**

스스로 회수할 수 없다(§10.1의 일곱 행이 그 회수를 매번 운영자에게 넘긴다). 이 한계는 이번 연속
노출의 원인이 아니라, **간격이 실제로 생겼을 때** 닫기를 운영자 입회에 묶는다. 재빌드는 여러 날에
걸칠 간격이 생길 가능성이 높으므로, 재빌드 예외에서 **회수를 운영자 sudo에 의존하지 않는 경로**로
개선한다(`docs/rebuild/HOST_EXCEPTIONS.md` §2.2).

**아직 하지 않은 것 (재빌드 이후 §9.2 완전 teardown 때).**
- `deluser ctf-spike-user && rm -rf <HOME>`, 스파이크 이미지·네트워크 삭제, 이미지 8개·디스크 6% 기준선 복귀.
- 최종 `<HOME>` 키 스윕(선택). 아키텍처상 0 보장 — 키는 컨테이너에 들어간 적 없고 매 run 0건.
- 경로 정정: 실제 데이터 디렉터리는 `<PROTO_HOME>/kisia-runs`이지 `kisia-data`가 아니다. `<PROTO_HOME>/`에는
  `archives git kisia-agent kisia-runs`만 있다.
